# SurvArena Benchmark Readiness Register

**Audit date:** 2026-09-01

**Evidence snapshot:** commit `fbcfc30ae5f3fb54770d9af3912fb0c16b74e8bb`, inspected in the live worktree. The required pre-edit guard snapshot recorded zero dirty repository paths; later documentation commits do not change the implementation evidence cited here.

## Verdict

SurvArena is a useful **internal benchmark framework and pre-release benchmark kernel**. It is **not yet a research/citable benchmark release**, and the current evidence is **not comprehensive or robust enough for manuscript-grade performance claims**. The public/maintained tier has deliberately not been attempted and is not a blocker for the accurately scoped local Python toolkit.

Four defects from the initiating audit have since been corrected in the live Phase 2 kernel: exact-cell pairwise matching, method-within-dataset ranks, dataset-level inferential counts, and dataset-shared fixed horizons with explicit support eligibility. Those corrections make the code materially stronger, but they also invalidate retained matrices generated before the behavior changes. The remaining blockers concern execution and group safety, truthful HPO semantics, immutable dataset and protocol identity, canonical provenance, independent release reproduction, and regeneration of all citable evidence.

**Highest target priority:** make one conflict-rejecting canonical result collection the only source for execution state, resume/retry, merge, comparison, and reporting. Until every table can be traced to one immutable collection that rejects divergent payloads, more benchmark compute cannot become durable evidence.

“Official” is meaningful here only relative to a named version, ruleset, accountable owner, and release process. The tiers below are a project maturity taxonomy, not an external certification. `[ASSUMED]`

## Scope and Re-Audit Triggers

This audit covers the maintained claim: single-event, right-censored tabular survival methods available through Python adapters. Competing risks, recurrent events, multi-state outcomes, interval censoring, left truncation, time-varying prediction, non-Python ecosystems, and an untrusted public submission service are outside that claim. Their absence is future scope, not a current defect. [VERIFIED: `.planning/PROJECT.md:44-50`]

The audit assesses benchmark design and release evidence; it is not an independent numerical validation of every metric, dataset, or adapter. Re-audit after any material change to the comparison kernel, protocol or execution semantics, dataset suite or method roster, report-generation path, or canonical release environment.

## Evidence Taxonomy and Provenance

- `OBSERVED DEFECT` requires direct live behavior, an executable counterexample, or a maintained artifact that is explicitly invalidated by a verified behavior change.
- `MISSING EVIDENCE` means the claim may be true, but it has not been demonstrated under the release contract. Configuration, intent, and pending requirements are not closure evidence.
- `FUTURE SCOPE` is deliberate work outside the present product claim. It becomes a gap only if the project broadens that claim.
- A VERIFIED provenance tag contains one canonical tracked repository-relative POSIX path and one inclusive line range. `[CITED]` identifies an adjacent authoritative external source. `[ASSUMED]` identifies project synthesis rather than a formal standard.
