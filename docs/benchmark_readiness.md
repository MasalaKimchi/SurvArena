# SurvArena Benchmark Readiness Register

**Audit date:** 2026-09-01

**Evidence snapshot:** commit `fbcfc30ae5f3fb54770d9af3912fb0c16b74e8bb`, inspected in the live worktree. The required pre-edit guard snapshot recorded zero dirty repository paths; later documentation commits do not change the implementation evidence cited here.

## Verdict

SurvArena is a useful **internal benchmark framework and pre-release benchmark kernel**. It is **not yet a research/citable benchmark release**, and the current evidence is **not comprehensive or robust enough for manuscript-grade performance claims**. The public/maintained tier has deliberately not been attempted and is not a blocker for the accurately scoped local Python toolkit.

Four defects from the initiating audit have since been corrected in the live Phase 2 kernel: exact-cell pairwise matching, method-within-dataset ranks, dataset-level inferential counts, and dataset-shared fixed horizons with explicit support eligibility. Those corrections make the code materially stronger, but they also invalidate retained matrices generated before the behavior changes. The remaining blockers concern execution and group safety, truthful HPO semantics, immutable dataset and protocol identity, canonical provenance, independent release reproduction, and regeneration of all citable evidence.

**Highest target priority:** make one conflict-rejecting canonical result collection the only source for execution state, resume/retry, merge, comparison, and reporting. Until every table can be traced to one immutable collection that rejects divergent payloads, more benchmark compute cannot become durable evidence.

“Official” is meaningful here only relative to a named version, ruleset, accountable owner, and release process. The tiers below are a project maturity taxonomy, not an external certification. `[ASSUMED]`

## Scope and Re-Audit Triggers

This audit covers the maintained claim: single-event, right-censored tabular survival methods available through Python adapters. Competing risks, recurrent events, multi-state outcomes, interval censoring, left truncation, time-varying prediction, non-Python ecosystems, and an untrusted public submission service are outside that claim. Their absence is future scope, not a current defect. [VERIFIED: `.planning/PROJECT.md:44-50`]

The audit assesses benchmark design and release evidence; it is not an independent numerical validation of every metric, dataset, or adapter. Re-audit after any material change to the comparison kernel, protocol or execution semantics, dataset suite or method roster, report-generation path, or canonical release environment.

## Evidence Taxonomy and Provenance

- `OBSERVED DEFECT` requires direct live behavior, an executable counterexample, or a maintained artifact that is explicitly invalidated by a verified behavior change.
- `MISSING EVIDENCE` means the claim may be true, but it has not been demonstrated under the release contract. Configuration, intent, and pending requirements are not closure evidence.
- `FUTURE SCOPE` is deliberate work outside the present product claim. It becomes a gap only if the project broadens that claim.
- A VERIFIED provenance tag contains one canonical tracked repository-relative POSIX path and one inclusive line range. `[CITED]` identifies an adjacent authoritative external source. `[ASSUMED]` identifies project synthesis rather than a formal standard.

## Evidence-Ranked Current Blockers

The current kernel has stronger comparison and metric behavior than the retained evidence bundle, but **it is still not ready for manuscript-grade claims**. The single highest priority is BR-009: establish one conflict-rejecting canonical collection as the source of truth. That work turns later compute, report regeneration, and independent reproduction into traceable evidence rather than another set of mutable files. The next scientific blockers are group-safe validation and truthful HPO or resource semantics; the next release blockers are immutable dataset identity, strict protocol identity, and independent reproduction.

This ordering is evidence-ranked, not merely feature-ranked. An observed defect that can change a conclusion outranks an undocumented convenience, while a missing release proof remains a blocker even when the underlying implementation may already be correct. Gate C and broadened-claim rows are deliberately separated from the current manuscript path.

## Decisions Needed Before Full Runs

1. **Claim purpose:** choose whether the release supports general practitioner model selection or a narrower method-comparison manuscript, then freeze the dataset, method, metric, and robustness scope that follows.
2. **Tuning target:** predeclare whether HPO optimizes one metric and horizon, a horizon aggregate, or another validation objective; do not select after observing test results.
3. **Default-only methods:** decide whether they form an explicitly labeled `default_only` arm or are excluded from tuned-arm comparisons. They must never appear as silently tuned.
4. **Common support:** retain complete-block headline comparison and separate reliability unless a different missingness policy is justified and frozen before compute.
5. **Canonical hardware and determinism:** name the release environment, accelerator policy, thread and resource limits, deterministic guarantees, tolerated nondeterminism, and replication thresholds.

## Maintenance Rules

- Allowed statuses are `open`, `in_progress`, `blocked`, `verified`, `accepted_risk`, `deferred_scope`, and `superseded`. `verified` requires observed evidence satisfying that row's exit criterion; configuration, intent, a pending requirement, or implementation completion alone is insufficient.
- `Benchmark maintainer` stewards prioritization and protocol integration; `Scientific-methods maintainer` owns estimands, statistics, and baselines; `Data steward` owns cohort identity and leakage controls; `Release steward` owns provenance, reporting, packaging, and reproduction; `Security maintainer` owns future untrusted-service boundaries. Reassign an owner explicitly when accountability changes.
- Preserve IDs after closure. When a finding splits, retain the parent as `superseded`, name every canonical replacement ID in that row after the words `Replaced by`, and keep its evidence history. Never delete audit history to make the register appear complete.
- Refresh `Last verified`, repository line ranges, dirty cited-file hashes, and external-source dispositions whenever evidence moves. A citation proves only the adjacent claim and must be re-read, not mechanically renumbered.
- Re-audit after a comparison-kernel change, protocol or execution-semantics change, dataset-suite or method-roster change, report-path change, canonical collection migration, or release-environment change.
- P2 `deferred_scope` rows and `Broadened claim` rows do not block Gate A or Gate B for the current accurately scoped package. Activate them only when the public-platform or scientific claim boundary changes.
